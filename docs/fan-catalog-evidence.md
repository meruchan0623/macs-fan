范围与机型别名复用 `catalog::matches_scope` 和 `catalog::normalize_model`，包括已经取证的数字拼接比较语义；不另写一套规则。例如 `Mac16,8` 根据 `evidence/deep/resources/idSwapRules.xml:36` 归一化为 `MacBookPro21,2`，再获得左右侧标签。JSON 的 `evidence` 同时记录位置来源及实际使用的别名来源。

规则顺序遵循首个匹配的机型块，不能套用传感器目录的后匹配覆盖语义。证据为 `evidence/fan-catalog/arm64-name-resolver.asm:121–134` 中的构造函数：`0x100033f84` 检查机型列表；`0x100033f88` 仅在不匹配时跳回下一个块；匹配后遍历 fan0…fan3，`0x100033fb4`/`0x100033fb8` 在索引到 4 后跳至 `0x100033e78` 清理退出。因此 `MacBookPro20,1` 命中较早的 `MacBookPro18,1+`，索引 0/1 来源为 XML 第 7/8 行，后面的精确规则不会覆盖。索引读取在同文件 `299–316`、入口为 `0x100034250` 的名称查询函数中执行边界检查（`0x100034268`、`0x100034274`）。当前九块的索引均从 0 连续排列。

目录只为 `FNum` 实际枚举出来的控制通道附加名称，不决定通道数量，不补造风扇行，不修改 F0/F1 等硬件 ID、转速、范围、目标或模式。未匹配的机型和未声明的索引保留“风扇 N”。“双风扇”描述一个控制通道对应的组件，不代表读到两个独立通道；该限制保存在可选 `note` 字段中。位置资料不构成硬件实测或控制授权。

测试覆盖首匹配遮蔽、别名与证据、索引边界、畸形机型、未知回退、双风扇不推导数量、实际读取管线中的硬件字段保留，以及旧 JSON 不含新增字段的反序列化兼容性。
